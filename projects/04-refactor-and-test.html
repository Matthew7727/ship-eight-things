Project 04 · Weeks 7–8

Refactor & test

No new features. Go back to the expense tracker and make it something you'd be happy to hand over.

refactor: make past-me's code liveable

This is the fortnight that feels least like progress and teaches the most. You're not adding anything. You're taking code you wrote a month ago — which you'll find surprisingly hard to read — and restructuring it without breaking it.

That skill, changing existing code safely, is most of what professional engineering actually is. Very little of the job is writing new things on blank pages.

Session 1

Read your own code

Before changing anything, open the expense tracker and read it start to finish. Keep a notes file open and write down every time you have to stop and work something out.

Look for: functions doing more than one thing, names that don't say what they hold, the same logic copied in two places, functions longer than about twenty lines, and anything you had to re-read twice.

This is the exercise

The discomfort of reading your own old code is the lesson. Every confusing bit is a decision that made sense at the time and doesn't now. That's what you're about to fix — and noticing it is a skill in itself.

Build this

A written list of everything wrong with it. Commit the notes file — it's evidence of how you think, and it'll be satisfying at the end of the fortnight.

You should now be able to

You have a concrete list of problems rather than a vague sense the code is messy.

Session 2

Your first test

Before changing code you need a way to know you haven't broken it. That's what tests are.

pip install pytest

A test is a function starting with test_ containing an assert — a statement of what should be true:

# test_tracker.py
from tracker import calculate_total

def test_total_of_two_expenses():
    expenses = [{"amount": 10.0}, {"amount": 5.50}]
    assert calculate_total(expenses) == 15.50

def test_total_of_empty_list_is_zero():
    assert calculate_total([]) == 0

Run them with pytest in your terminal. Green means passing, red means something's wrong.

Run pytest -v for verbose output — it prints each test name and whether it passed or failed. Use pytest -k "total" to run only tests with "total" in their name — useful when you want to focus on one area.

When a test fails, read the output carefully. It tells you: which test failed, which line, what the actual value was, and what was expected. The first number on the assertion line is always what your code returned; the second is what you expected. That ordering matters.

Each test has three parts: set up the situation, do the thing, check the result. Name tests so a failure tells you what broke without reading the code — test_total_with_negative_amount is better than test_case_7.

Build this

Write tests for every function that returns a value. For each function, cover: the normal case, an empty list or zero input, a negative amount, a single-item list, a list with duplicate categories, and a description containing special characters or unicode. Run with pytest -v so you can see all the names. Aim for at least 12 tests before you move on.

You should now be able to

pytest -v runs and passes, you can read a failing test's output and understand exactly what went wrong, and you know what -k does.

Session 3

The safety net

Tests only help if they cover the behaviour you're about to change. So before refactoring anything, get the current behaviour under test — including the bits you think are ugly.

You'll hit a problem: some functions can't be tested because they do too much. A function that reads input, calculates and prints has no return value to assert on. That's not a testing problem, it's a design problem, and the test is what revealed it.

The useful insight

Hard-to-test code is badly structured code. Testability isn't a separate quality you add — it's a symptom of good separation. If you can't test it, split the calculating from the printing and test the calculating.

Test what the function does, not how it does it. A test that breaks when you rename an internal variable is a test that will annoy you forever. This is called the test boundary — you test inputs and outputs, not the internal implementation. Anything inside the function can be reorganised, renamed, or replaced as long as the observable behaviour stays the same.

When you need to test something that calls other functions (like a save function that calls the OS), unittest.mock lets you replace those collaborators with a fake:

from unittest.mock import mock_open, patch

def test_save_writes_correct_json():
    expenses = [{"description": "Coffee", "amount": 3.40}]
    m = mock_open()
    with patch("builtins.open", m):
        save_expenses(expenses, "test.json")
    handle = m()
    written = handle.write.call_args[0][0]
    assert "Coffee" in written

This is a more advanced technique — don't spend more than an hour on it this session. The point is knowing it exists so you're not stuck when a function you want to test touches a file or the network.

Build this

Every calculation function under test. Split any function that mixes input, logic and output so the logic is in the middle and testable. If a function truly can't be isolated, note it in a comment and move on — you'll refactor it properly in session 6.

You should now be able to

You can change the inside of any calculation function and the tests will tell you if you broke it. You can explain the test boundary.

Session 4

Classes

You've been passing the same list of expenses into every function. A class bundles data together with the functions that work on it.

class ExpenseBook:
    def __init__(self):
        self.expenses = []

    def add(self, description, amount, category):
        self.expenses.append({
            "description": description,
            "amount": amount,
            "category": category,
        })

    def total(self):
        return sum(e["amount"] for e in self.expenses)
book = ExpenseBook()
book.add("Coffee", 3.40, "food")
print(book.total())

__init__ runs when you create one. self means "this particular book" — it's how each instance keeps its own data. Functions inside a class are called methods.

Methods with double underscores on both sides (like __init__) are called dunder methods — Python calls them automatically in certain situations. Two more worth knowing now:

def __repr__(self):
    return f"ExpenseBook({len(self.expenses)} expenses)"

def __len__(self):
    return len(self.expenses)

__repr__ controls what you see when you print an object or view it in a debugger — invaluable for understanding what's happening. __len__ makes len(book) work. These aren't magic — they're just methods Python knows to call in the right situations.

Classes aren't automatically better. They're useful when data and behaviour belong together — which is exactly the case here.

Build this

Build ExpenseBook with these methods: add, remove (by index), total, by_category (returns a dict of category → total), filter (takes a predicate function), to_dict (returns the expenses as a list of dicts for serialisation), from_dict (class method that builds a book from a list of dicts), __repr__, and __len__. Keep the tests green the whole way through.

You should now be able to

You can explain what self does without reciting a definition, and you can explain what dunder methods are and name three examples.

Session 5

Splitting into files

One long file is fine until it isn't. Split by responsibility:

expense_tracker/
  main.py         # menu loop, talks to the person
  expense_book.py # the class, all the logic
  storage.py      # loading and saving JSON
  test_book.py
  test_storage.py

Import across files by filename:

from expense_book import ExpenseBook
from storage import load, save

The division that matters: main.py is the only file that talks to a human. Everything else just works with data. That's why the rest is testable — and it's the same separation that will let you put a web interface on it in project 5 without rewriting the logic.

When you split into multiple files in the same folder, Python treats that folder as a package if it contains an __init__.py file (even an empty one). Without it, imports can get confusing when you run tests from different directories. Add an empty __init__.py and your import paths become consistent.

One thing to watch: circular imports. If expense_book.py imports from storage.py and storage.py imports from expense_book.py, Python can't resolve it — you get an ImportError or silent failures. The fix is to organise so data flows one direction: storage.py knows nothing about ExpenseBook, it just handles files. expense_book.py uses storage but storage doesn't use the book.

Build this

Split into modules with an __init__.py. Tests still green. Everything still works. Logic files contain no print or input at all.

You should now be able to

Your logic files contain no print or input. You can explain what __init__.py does and what a circular import is.

Challenge

No hints — type hints and mypy

This one is on you

You haven't been shown how to do this. Use the Python docs, the mypy docs, and the error messages. That process — reading docs, interpreting errors, making them go away — is what engineering actually is most of the time.

Add type hints to every function and class in your codebase. Then install mypy and run it:

pip install mypy
mypy expense_book.py storage.py

Fix every error mypy raises. The goal is zero errors with --strict off (don't add --strict, just run plain mypy). Some errors will be obvious once you read them. Others will require looking things up. That's the point.

You're done when

mypy expense_book.py storage.py outputs "Success: no issues found" and all your tests still pass.

Session 6

Refactor for real

Now the safety net is in place, go through your week-one list of problems and fix them properly. The discipline:

  1. Make one small change
  2. Run the tests
  3. Green? Commit. Red? Undo it and go smaller.

Never make two changes at once. When something breaks you want to know exactly what caused it.

The temptation to start over

At some point you'll want to delete it and rewrite from scratch. Don't. Rewriting is easy and teaches you nothing; changing working code without breaking it is the actual skill, and it's the one you'll use every week of your career.

Once you've fixed the list from session 1, add a GitHub Actions workflow so tests run automatically on every push:

# .github/workflows/tests.yml
name: Tests
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install pytest
      - run: pytest

Push it. Watch the Actions tab go green. Add the badge to your README so it shows the current status.

Build this

Work through the session-1 list. Commit after each fix. Set up GitHub Actions. Finish by re-reading the notes file from session 1 and adding a paragraph on what changed and what you'd do differently if you were starting over.

You should now be able to

20+ tests pass, code is across at least 4 modules, no print/input outside main.py, GitHub Actions is green, and the README has the CI badge.

Traps to avoid

Deleting and rewriting

Not refactoring. The skill is changing code safely, in steps, with the tests green.

Testing the inside

If renaming a private variable breaks a test, the test is testing the wrong thing. Test behaviour.

Classes everywhere

Not everything needs to be a class. A function that takes some data and returns an answer is often just better.

If you finish early

  • Add a test that checks loading and saving round-trips correctly.
  • Use pytest fixtures to avoid repeating setup in every test.
