Project 08 · Weeks 15–16

Add a brain

An AI feature that survives the model being slow, wrong, or unavailable.

feat: build something with a language model

Calling a language model API is easy — it's a few lines. The engineering is everything around it: what happens when it's slow, when it returns something malformed, when it's confidently wrong, and when it costs more than you expected.

That's what this fortnight is about. The API call is the least interesting part.

Session 1

Your first model call

Get an API key from Anthropic or OpenAI, put it in .env, and set a spending cap on the account before you write a line of code.

import os
from anthropic import Anthropic

client = Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))

message = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=200,
    messages=[{"role": "user", "content": "Categorise this expense: 'Coffee at Pret'"}],
)
print(message.content[0].text)

You pay per token — roughly three-quarters of a word. Both what you send (input tokens) and what comes back (output tokens) are billed. They're usually priced differently — input is cheaper. max_tokens caps the reply length, which caps the output cost. A small response cap matters for a categorisation feature; it matters much less for a summarisation feature that legitimately needs long output.

Token counts also determine what the model can "see". Models have a context window — a maximum total of input plus output tokens per call. If you send too much context, the call fails. In practice for this project you'll be nowhere near the limit, but knowing it exists matters when you later deal with long documents or conversation histories.

You can see a rough token count in the API response: message.usage.input_tokens and message.usage.output_tokens. Log these during development so you're not surprised by costs.

Hosted, not local

You can't run a useful model on 8GB of memory. That's a hardware limit, not a skill one — and hosted APIs are what nearly all production systems use anyway. A project like this costs pennies.

Build this

A script that sends a prompt and prints the answer. Then print the token counts too. Check your usage dashboard afterwards and note the actual cost. This number will inform how you think about caching and max_tokens for the rest of the project.

You should now be able to

You can call the API, you know how you're being charged, you understand the difference between input and output tokens, and you know what a context window is.

Session 2

Prompts as inputs you design

A prompt is an input to your program, so treat it with the same care. Vague prompts give inconsistent output, and inconsistent output is unusable in code.

What helps: be specific about the task, state the exact options, give an example, and say what to do when unsure.

prompt = f"""Categorise this expense into exactly one category.

Categories: food, travel, bills, entertainment, other

Rules:
- Reply with the category name only, nothing else
- If genuinely unclear, reply: other

Expense: {description}"""

The API has a system parameter for standing behaviour and a messages list for the specific task. Separating them matters: the system prompt sets who the model is and what it's doing; the user message carries the data. This makes both easier to modify independently.

Temperature controls how random the output is. At 0 the model picks the most likely token every time — good for classification and structured output where you want consistency. At higher values it explores less likely options — good for creative tasks. For this feature, set temperature to 0 or close to it.

Few-shot prompting means including examples in the prompt. If you show the model three examples of the pattern you want, it follows the pattern much more reliably than if you only describe it:

system = """You categorise expenses. Reply with the category only.

Examples:
Coffee at Costa → food
Train to London → travel
Netflix subscription → entertainment
Council tax → bills
Birthday present for Mum → other"""
Build this

Test your prompt against at least 30 real expense descriptions, including deliberately awkward ones. Keep all the failures in a file called test_cases.txt. Iterate the prompt until it gets at least 90% correct. Write a comment in the code explaining the key change that improved accuracy most — this is your prompt engineering log.

You should now be able to

The same input gives the same category, you've seen where it struggles, and you've used few-shot examples and temperature to improve consistency.

Session 3

Structured output, and never trusting it

Prose is no use to a program. Ask for JSON:

prompt = """Return only valid JSON, no other text:
{"category": "food|travel|bills|entertainment|other",
 "confidence": "high|medium|low"}"""

Then treat what comes back as untrusted input, because that's exactly what it is:

import json

VALID = {"food", "travel", "bills", "entertainment", "other"}

def parse_response(text):
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return {"category": "other", "confidence": "low"}

    if data.get("category") not in VALID:
        return {"category": "other", "confidence": "low"}

    return data
This is the whole lesson

Models return malformed JSON, invent categories you never offered, and wrap answers in explanation you didn't ask for. Always validate. Always have a fallback. Code that assumes a well-formed response will break in production, and it'll break on a Saturday.

Never use eval() on model output — it executes arbitrary code. Even if the output looks like Python, json.loads is the correct tool, and it only handles JSON, not Python expressions.

For more complex schemas, consider a validation library. pydantic lets you define the expected shape as a class and will raise a clear error if the data doesn't match:

from pydantic import BaseModel

class CategoryResult(BaseModel):
    category: str
    confidence: str

try:
    result = CategoryResult(**data)
    if result.category not in VALID:
        raise ValueError
except Exception:
    result = CategoryResult(category="other", confidence="low")

This is optional for this project, but knowing it exists is useful — Pydantic is widely used in production AI applications for exactly this purpose.

Build this

Structured output with full validation. Force failures deliberately: send malformed JSON in a test, send a response with an invalid category, send an empty string. Make sure your fallback holds in every case without crashing.

You should now be able to

Your app cannot be broken by the model returning something unexpected. You can explain why eval() is wrong here.

Session 4

Wiring it into the app

Add the feature to project 7. Keep the model call in its own module — a function that takes text and returns a validated result. Your routes shouldn't know which provider you're using.

# ai.py
def suggest_category(description: str) -> str:
    ...returns a valid category, always...

That separation means you can swap providers, or replace it with a fixed answer in your tests, without touching the rest of the app. Tests that call a real API are slow, flaky and cost money. Use a mock client instead:

from unittest.mock import MagicMock

def test_suggest_category_returns_food():
    mock_client = MagicMock()
    mock_client.messages.create.return_value.content[0].text = '{"category": "food", "confidence": "high"}'
    result = suggest_category("Coffee", client=mock_client)
    assert result == "food"

This requires passing the client as a parameter to your function (dependency injection). It makes the function testable and the dependency explicit.

Make it a suggestion, not a decision

Pre-fill the category dropdown with the AI's suggestion and let the person change it. AI features that quietly decide things are infuriating when they're wrong — and they will sometimes be wrong.

Build this

The AI feature in its own module with dependency injection, tested with a mock client (no real API calls in tests), integrated into the web app as a suggestion pre-filling the category dropdown — not auto-selecting it, not hiding the override option.

You should now be able to

You could swap providers by changing one file. The tests pass without making any real API calls. The user always has the option to override the suggestion.

Challenge

No hints — natural-language search

This one is on you

You know the full stack now. Make a decision, implement it, and explain it. No example code.

Add a natural-language search box to your expense app. A user types something like "all the coffees last month" and gets back matching expenses.

You need to make a design decision first. There are two viable approaches:

  • Approach A: Send the user's query to the AI, ask it to convert the query into a SQL WHERE clause, execute that clause against the database.
  • Approach B: Fetch all expenses for the user, send them to the AI along with the query, and ask the AI to return the matching ones.

Both approaches work. Both have real tradeoffs. Implement one, then add a section to your README titled "Natural-language search: approach and tradeoffs" that explains which you chose, why, and what the other approach would be better for.

You're done when

The search box works for at least three different natural-language queries, the README explains the tradeoffs, and the feature degrades gracefully if the AI is unavailable.

Session 5

Slow, broken, and expensive

Model calls take seconds, not milliseconds. Without a loading state your app looks frozen and people click twice.

try:
    result = suggest_category(description)
except APITimeoutError:
    result = None          # carry on without it
except APIError:
    result = None

The pattern that matters: the AI feature failing must not break the app. If the model is down, adding an expense should still work — just without a suggested category. Degrade, don't collapse.

On cost: what does a reasonable SLA (service level agreement) look like for an AI feature? If your categorisation call costs 0.01p and takes 800ms, you need to decide: is that acceptable for every expense entry? Can you cache repeated descriptions? A simple exact-match cache can cut API calls significantly if users tend to add similar expenses:

_cache = {}

def suggest_category_cached(description: str) -> str:
    key = description.lower().strip()
    if key in _cache:
        return _cache[key]
    result = suggest_category(description)
    _cache[key] = result
    return result

This is an in-memory cache — it resets on restart. For a production app you'd use Redis or the database. But this version is fine here and costs nothing.

If you wanted lower latency and the model supports it, streaming lets you display the response as it's generated rather than waiting for the full thing. Worth knowing the concept exists.

Build this

Loading indicator while the AI call runs, timeout handling, graceful degradation (test deliberately with a wrong API key), and a simple in-memory cache. Log the token counts and cache hit rate to the console during development so you can see it working.

You should now be able to

Break the API on purpose and the rest of the app carries on. You can explain what SLA means in this context and why caching helps.

Traps to avoid

Trusting the output

Validate everything. Always have a fallback.

No timeout

A hanging model call hangs your whole page.

Letting AI failure break the app

The feature is optional. The app isn't.

No spending cap

Set one before your first call, not after your first bill.

If you finish early

  • Stream the response so text appears as it's generated.
  • Let the person correct a suggestion and store the correction to improve future suggestions.
  • Log every prompt and response to a database table so you can debug odd behaviour later.
