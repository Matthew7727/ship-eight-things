Project 03 · Weeks 5–6

Weather client

Your first program that reaches outside your own machine. APIs, keys, and things going wrong.

feat: talk to the internet

Everything you've built so far runs entirely on your laptop. This one talks to a server somewhere else, which introduces a whole category of problems: the network fails, the server is slow, the data isn't the shape you expected, and you have a secret key you must not leak.

All of that is normal professional work. This is the project where your code stops being self-contained.

Session 1

Installing packages, and your first request

Before installing anything, understand what HTTP actually is. Every time your browser visits a page, it sends a message over the network that looks roughly like this:

GET /api/weather?city=London HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0

That's a request: a method (GET), a path, a protocol version, and some headers. The server sends back a response: a status code, headers, and a body. requests is a Python library that builds and sends these messages for you, so you don't have to format them by hand.

You can see the raw version using curl in your terminal — it does what requests does, but from the command line. Try it before you write a single line of Python:

curl -i https://api.github.com

The -i flag shows the headers. You'll see the status line, the headers, and the JSON body — that's the exact thing requests parses for you.

Status code ranges worth memorising: 2xx = success (200 OK, 201 Created), 3xx = redirect, 4xx = your fault (400 Bad Request, 401 Unauthorised, 404 Not Found, 429 Too Many Requests), 5xx = their fault (500 Internal Server Error).

source .venv/bin/activate   # always activate first
pip install requests
If pip says it's already installed but Python can't find it

You've installed into a different environment than the one you're running. Check your prompt starts with (.venv). This is the most common environment confusion there is.

import requests

response = requests.get("https://api.github.com")
print(response.status_code)   # 200 means OK
print(response.json())
Build this

First: run the curl command above and read what comes back. Then: install requests, call any public API, print the status code and the response body. Before you move on, look at the response.headers dict — it tells you things like the content type and the server software.

You should now be able to

You can explain what an HTTP request and response are, install a package, and make a request from Python. You know the status code ranges.

Session 2

Getting a key, and keeping it secret

Sign up for a free OpenWeatherMap account and get an API key. It's a string that identifies you — treat it exactly like a password.

It must never go in your code, because your code goes on GitHub. Instead, put it in a file called .env:

WEATHER_API_KEY=your_actual_key_here

An environment variable is a key-value pair the operating system makes available to any program it runs. They're not Python-specific — every language and every tool can read them. When you run python3 weather.py, Python can see everything in your environment. The .env file is just a convenient way to set them for one project without polluting your whole system.

Two ways to read them in Python:

import os

os.environ["WEATHER_API_KEY"]   # raises KeyError if missing
os.getenv("WEATHER_API_KEY")    # returns None if missing
os.getenv("WEATHER_API_KEY", "fallback")  # returns fallback if missing

Use os.environ when the key must be present — you want a hard crash on startup if it's missing, not a silent None that fails somewhere else later. Use os.getenv when a fallback makes sense.

Make sure .env is listed in your .gitignore — check with git status, it should not appear. Then load it:

pip install python-dotenv
from dotenv import load_dotenv

load_dotenv()
api_key = os.environ["WEATHER_API_KEY"]

Also commit a .env.example with the key names but no values, so anyone cloning your repo knows what they need.

If you commit the key anyway

It happens. Go to the provider, revoke that key, generate a new one. Don't just delete the line and commit again — it's still in your history, and bots scan public repos for exactly this within minutes.

Build this

Key in .env, .env ignored by git, .env.example committed, key loading correctly in Python using os.environ (so it crashes clearly if missing rather than silently passing None to the API call).

You should now be able to

git status never shows .env, your program reads the key, and you can explain the difference between os.environ and os.getenv.

Session 3

Reading the docs, and query parameters

Nobody memorises APIs. You read the documentation, and there's a method to it. When you find a new API, work through these questions in order:

  1. Base URL. What's the root address? (e.g. https://api.openweathermap.org/data/2.5)
  2. Endpoint. What path gives you what you need? (e.g. /weather for current, /forecast for multi-day)
  3. Required vs optional parameters. Which ones must you send? Which ones change the format?
  4. Example response. Find a sample in the docs. Look at the actual shape before you write any parsing code.
  5. Rate limits and error formats. How many calls per minute? What does a 401 response body look like?

Extra information goes on the end of a URL as query parameters — ?city=Manchester&units=metric. requests builds those for you:

params = {
    "q": "Manchester",
    "appid": api_key,
    "units": "metric",
}
response = requests.get(BASE_URL, params=params)

That's much safer than gluing strings together, and it handles spaces and odd characters properly.

A habit worth forming

Print the whole response the first time. Don't guess the shape of the data — look at it. print(json.dumps(data, indent=2)) makes it readable.

Build this

Two things: (1) Fetch real weather for a hardcoded city, print the full raw response with json.dumps(data, indent=2), and study it carefully before writing anything else. (2) Write a separate parse.py that imports the raw response (save it to a JSON file first so you're not hitting the API repeatedly) and extracts every field the docs mention — not just temperature and description, but wind direction, pressure, visibility, cloudiness, everything. Print the complete picture.

You should now be able to

You can read API docs methodically and construct a working request. You've looked at the full response shape before writing any parsing.

Session 4

Digging into nested data

API responses are dictionaries inside lists inside dictionaries. Getting a value means walking down through them:

data = response.json()

temperature = data["main"]["temp"]
description = data["weather"][0]["description"]

Read that second line as: from data, take the weather key, which is a list; take its first item, which is a dictionary; take the description from that.

Every step is a place it can break. If a field might be missing, .get() won't crash:

wind = data.get("wind", {}).get("speed", "unknown")

Think about this defensively. APIs change — fields get added, renamed, or removed. A field present in 99% of responses might be absent in the 1% that causes your program to crash at 2am. The rule: use .get() with a sensible fallback for any field that isn't guaranteed in the API documentation. If the docs say "optional", use .get().

Build this

Pull out temperature, description, humidity, wind speed, and the next-12-hours precipitation total. Format the output as a terminal dashboard — aligned labels, sensible units, clear layout. Then make the city a command-line argument using sys.argv or argparse.

You should now be able to

You can navigate nested JSON confidently, know where it might break, and apply defensive access to optional fields.

Session 5

When things go wrong

Your program works. Now try it with the wifi off, with a made-up city, with the key deleted. It'll crash three different ways, and handling that is what separates a script from a tool.

try:
    response = requests.get(BASE_URL, params=params, timeout=10)
    response.raise_for_status()
except requests.exceptions.ConnectionError:
    print("Can't reach the weather service. Check your connection.")
except requests.exceptions.Timeout:
    print("The weather service took too long to answer.")
except requests.exceptions.HTTPError:
    if response.status_code == 404:
        print("No city by that name.")
    elif response.status_code == 401:
        print("API key rejected.")
    else:
        print("Something went wrong at their end.")

Note the timeout. Without one, your program can hang forever waiting for a server that's never going to answer. Always set one on a network call.

What a good error message does

It says what happened and what to do about it. "Error" says neither. Write them for a person who has no idea how your program works.

Build this

Handle no internet, bad city, bad key and timeout — each with its own message. Test all four deliberately.

You should now be able to

Your program never shows a raw traceback to the person using it.

Challenge

No hints — five-day forecast

This one is on you

You know how to call an API, read docs, parse nested JSON, and handle errors. Now do all of it without guidance. Read the docs, print the raw response, figure out the shape, then build it.

Add a five-day forecast to your weather client. The OpenWeatherMap /forecast endpoint returns data in 3-hour intervals. You need to:

  1. Read the docs for the /forecast endpoint
  2. Fetch the data and print the raw response to understand the shape
  3. Group the 3-hour intervals into days
  4. For each day, print one summary line: the date, the high temperature, the low temperature, and the dominant weather condition (the one that appears most often across the day's intervals)

Activate with a --forecast flag or a separate command. Handle errors the same way as the current weather command.

You're done when

Running the program with a real city name prints a 5-day forecast with one clean summary line per day.

Session 6

Making it shareable

Someone else needs to be able to run this. Record what it depends on:

pip freeze > requirements.txt

Commit that file. Now anyone can recreate your environment with pip install -r requirements.txt.

Check it works by pretending to be them: clone your own repo into a different folder, make a fresh virtual environment, install from the file and run it. This catches things you forgot — it usually catches at least one.

Add a --json flag so the program can output raw data instead of a formatted summary. This is useful for piping into other tools or debugging. If --json is passed, skip all formatting and just print the raw API response.

Also save one real API response to a file called sample_response.json and commit it. This lets you develop the parsing code offline without burning API calls on every run.

Build this

requirements.txt committed, README covering how to get a key and set up .env, a genuine clean-clone test that you've actually done, a --json flag for raw output, and sample_response.json in the repo for offline development.

You should now be able to

A stranger could clone your repo and have it running in five minutes. You can work on the parsing code without internet access.

Traps to avoid

Assuming the response shape

Print it. Every time. APIs change and documentation lags behind.

No timeout

A network call without a timeout can hang forever. Always set one.

Hammering the API while debugging

Free tiers have limits. Save one response to a JSON file and work against that while you build the parsing.

If you finish early

  • Cache the last response so repeated runs don't re-fetch within a few minutes.
  • Accept several cities at once and compare them side by side.
  • Show wind direction as a compass point (N, NE, E…) not just degrees.
