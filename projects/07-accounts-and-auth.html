Project 07 · Weeks 13–14

Accounts & auth

Your portfolio piece. Something you'd actually use, with real user accounts.

feat: multiple users, real accounts

This is the project you'll talk about in interviews, so build something you care about — a habit tracker, a reading log, a five-a-side organiser, a recipe box, a running log. It only has to matter to you.

By week 13 the novelty has completely gone. Genuine interest in what you're building is what gets you through the fortnight.

Session 1

Design before you build

Start on paper. What are the things in your app, what does each one need to know, and how do they relate?

For a reading log: a user has an email and a password hash; a book has a title, an author, a status and a rating — and belongs to a user.

That "belongs to" is a foreign key — a column holding another table's id:

CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE books (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    title TEXT NOT NULL,
    status TEXT DEFAULT 'to-read',
    FOREIGN KEY (user_id) REFERENCES users(id)
);

Sketch the pages too. Four or five is plenty: sign up, log in, the main list, add, edit.

Build this

A written data model and a rough sketch of each page. Commit it — deciding before building is the professional habit.

You should now be able to

You can explain your tables and how they relate before writing any code.

Session 2

Passwords, done properly

You never store a password. You store a hash — a one-way transformation that can't be reversed. When someone logs in, you hash what they typed and compare hashes.

from werkzeug.security import generate_password_hash, check_password_hash

hashed = generate_password_hash(password)      # on sign-up
ok = check_password_hash(hashed, attempt)      # on log-in

That's the whole thing. The library handles salting and choosing a slow algorithm — both of which matter and neither of which you should implement yourself.

Here's why they matter. Old hash functions like MD5 and SHA-1 were designed to be fast — great for checksums, terrible for passwords. An attacker with a leaked database and a modern GPU can try billions of MD5 hashes per second. Password hashing functions like bcrypt are deliberately slow — they have a cost factor that controls how much work each hash requires. More work = slower attack.

A rainbow table is a pre-computed lookup of common passwords → their hashes. Without protection, if two users have the same password, their hashes look identical — and a single rainbow table entry cracks both. A salt is a random value mixed into the hash so that the same password produces a different hash every time. generate_password_hash generates a unique salt automatically.

The terminology: hashing is one-way (no key, can't reverse). Encryption is two-way (has a key, can be decrypted). Encoding (like base64) is a format change with no security — it's not secret. Passwords are hashed. If you ever meet a service that can email you your existing password, they've stored it in plain text or encrypted it — both wrong.

Why this is worth understanding, not just copying

Databases leak. Regularly. If yours leaks with plain-text passwords, you've handed over credentials that many people reuse on their email and their bank. Hashing means an attacker gets a pile of useless strings. It's the difference between an embarrassing incident and a serious one.

Build this

Working sign-up with: an email format check (must contain @ and a dot after it), a uniqueness check (return a clear error if the email is already registered), a password confirmation field that must match, a minimum password length of 8, and a users table with id, email, password_hash, created_at. Check the database after sign-up — you should see gibberish where the passwords are.

You should now be able to

You can explain hashing vs encryption vs encoding, why MD5 is wrong for passwords, what a salt does, and what bcrypt's cost factor is for.

Session 3

Logging in, and staying logged in

HTTP forgets you between requests, so after a successful log-in you store something in a session — a small signed cookie Flask manages for you.

from flask import session

# after checking the password
session["user_id"] = user["id"]

# logging out
session.clear()

Flask signs the cookie with your SECRET_KEY so nobody can tamper with it. The cookie itself is readable — it's just base64-encoded JSON. But the signature means that if someone changes even one character, Flask rejects it. So the contents aren't hidden, but they can't be faked without knowing the key.

Session fixation is an attack where a malicious site tricks a user into using a session ID they've already seen. The defence is to generate a new session after login — Flask does this when you call session.regenerate() or clear and rebuild. Worth knowing the name.

CSRF (Cross-Site Request Forgery) is when an attacker tricks a user's browser into making a POST request to your site while they're logged in. Since the browser sends cookies automatically, the request looks legitimate. The defence is a CSRF token — a random value included in every form that must match a value in the session. Flask-WTF handles this for you. It's worth knowing what it's protecting against even if you're not using Flask-WTF yet.

Vague log-in errors are deliberate

Say "email or password is incorrect", never "no account with that email". The second version lets someone test which addresses are registered. This is called user enumeration and it's worth knowing the name.

Build this

Log in, log out, and a page that shows who you are when you're logged in. Make sure the error message says "email or password is incorrect" — never tell the user which part was wrong.

You should now be able to

You can log in, close the tab, come back and still be logged in. You can explain what's in the cookie, what session fixation is, and what CSRF is.

Session 4

Protecting pages

Now stop logged-out people reaching pages they shouldn't. A decorator lets you mark routes as protected:

from functools import wraps

def login_required(f):
    @wraps(f)
    def wrapped(*args, **kwargs):
        if "user_id" not in session:
            return redirect(url_for("login"))
        return f(*args, **kwargs)
    return wrapped

@app.route("/books")
@login_required
def books():
    ...

Decorators look strange the first time. All this one does is wrap your function in a check that runs first.

Apply @login_required to every route that shows or changes data. Test it by logging out and typing the URL directly — every single protected URL should redirect you to login.

Now write a second decorator for item-level routes — one that checks not just that you're logged in, but that the item in the URL belongs to you. This query is the right pattern:

# correct — checks both login and ownership in the database
"SELECT * FROM books WHERE id = ? AND user_id = ?"

Build this as a helper function rather than a decorator if that's cleaner — what matters is that every item-level route runs the ownership check.

Build this

@login_required applied to every route that shows or changes data. Every item-level route (view, edit, delete by ID) checks ownership in the database query itself — not just in application code. Test both by logging out and by creating two accounts.

You should now be able to

There's no URL a logged-out person can reach that shows anything private, and no logged-in person can access another user's items.

Session 5

The bug almost everyone ships

Log in as user A, open one of your items, and look at the URL — /books/7. Now log in as user B and type that same URL.

If you can see user A's book, you have an IDOR — insecure direct object reference. You checked whether someone was logged in, but never whether this logged-in person owns that record.

# not enough
"SELECT * FROM books WHERE id = ?"

# correct
"SELECT * FROM books WHERE id = ? AND user_id = ?"

IDOR applies everywhere you touch data by ID. Three concrete examples:

  • Viewing: /books/7 — can user B read user A's book?
  • Editing: POST /books/7/edit — can user B modify user A's book title?
  • Deleting: POST /books/7/delete — can user B delete user A's book entirely?

The fix must be at the database query level. Checking if item["user_id"] == session["user_id"] in Python after fetching the row is a common approach and it works — but checking in the SQL query is better because it avoids fetching the row at all. A row that doesn't belong to you should simply not come back from the database.

Authentication vs authorisation

Authentication answers "are you logged in?" — your login check. Authorisation answers "are you allowed to touch this?" — the ownership check. Most beginners implement authentication but skip authorisation. The result: any logged-in user can edit or delete any other user's data by guessing IDs in the URL. Always check both.

Build this

Audit every route. Create two accounts and genuinely try to break into one from the other — including view, edit and delete, not just viewing. Every item-level query must include the AND user_id = ? check. Document your audit in the README: which routes you checked and what you found.

You should now be able to

Two accounts, tested by hand, and no URL exposes or modifies anyone else's data. You can explain the difference between authentication and authorisation.

Challenge

No hints — rate limiting on login

This one is on you

You know SQL, sessions, and the request cycle. Now apply them to a real security problem. No example code.

Add rate limiting to the login route. The requirements:

  • After 5 failed login attempts from the same IP address within 10 minutes, lock that IP out for 30 minutes
  • Show a clear message explaining why login is blocked and when the lockout ends
  • Successful logins reset the failed attempt count for that IP
  • You'll need to store attempt counts somewhere — a new database table is one option

Think through the edge cases: what if the server clock changes? What if someone legitimately fails 4 times then succeeds? What if someone bypasses this using a VPN or shared WiFi? Implement the feature, then add a section to your README noting the limitations.

You're done when

Five failed attempts in 10 minutes triggers a lockout, the message is clear and includes when the lockout ends, and the README documents the limitations.

Session 6

Finish and deploy

Deploy it, then write the README as though a hiring manager will read it — because one might.

Cover: what it does and why you built it, a screenshot, the live link, how to run it locally, the data model (even a hand-drawn photo), and an honest "what I'd do differently". That last section is the one that makes people take you seriously.

Add test accounts to the README so someone can look around without signing up.

Add a section titled "Security decisions" that explains: why passwords are hashed and not encrypted, why the login error is vague, how IDOR is prevented in the queries, and what the rate limiting limitation is. This section demonstrates that you made deliberate choices, not accidental ones.

Add a section titled "What's still missing" that honestly lists what a production app would need that yours doesn't have — email verification, password reset flow, rate limiting improvements, HTTPS-only cookies, CSP headers. Honesty here is a strength, not a weakness.

Build this

Deployed, README written for a hiring manager, test accounts included, "Security decisions" section, "What's still missing" section, and the link sent to someone who'll actually use it.

You should now be able to

Live, secure as far as it goes, and documented well enough to show a stranger.

Traps to avoid

Writing your own password hashing

Use the library. Then read about why.

Checking login but not ownership

The IDOR bug. Test it with two accounts, by hand, every time.

SECRET_KEY in the code

Environment variable. If it leaks, sessions can be forged.

Building something you don't care about

Week 13 is late. Motivation has to come from the project itself.

If you finish early

  • Add a password reset flow via email.
  • Let users share one item publicly with a secret link.
  • Add HTTPS-only cookies (SESSION_COOKIE_SECURE = True) and explain what this protects against.
Definition of doneTwo accounts see two different sets of data, passwords are hashed, no URL leaks or modifies another user's records, rate limiting is in place, and it's live.
Raise an MROpen a pull request on this repository with your auth app. The MR description must include a security checklist, which you must complete honestly: (1) passwords hashed — confirmed by checking the database directly; (2) no user enumeration on login — confirmed by testing both "wrong email" and "wrong password"; (3) every protected route tested by logging out and navigating directly; (4) IDOR tested with two accounts on every route that touches data by ID (list which routes). The MR will not be merged until all four are checked off with evidence.
