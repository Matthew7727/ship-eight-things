Project 06 · Weeks 11–12

Database & deploy

Swap the JSON file for SQL, then put the whole thing on the internet.

feat: real database, live on the internet

Two milestones in one fortnight. First a real database, because a JSON file falls apart the moment two people use it at once. Then deployment — the first thing you've built that someone else can open on their phone.

Expect the deployment day to be frustrating. It is for everyone, every time.

Session 1

SQL basics

SQLite comes with Python and stores a whole database in one file. Open one in your terminal:

sqlite3 expenses.db

Data lives in tables — columns define what a row can hold:

CREATE TABLE expenses (
    id INTEGER PRIMARY KEY,
    description TEXT NOT NULL,
    amount REAL NOT NULL,
    category TEXT,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

PRIMARY KEY means unique identifier, filled in automatically. NOT NULL means required.

INSERT INTO expenses (description, amount, category)
VALUES ('Coffee', 3.40, 'food');

SELECT * FROM expenses;
SELECT * FROM expenses WHERE category = 'food';
SELECT * FROM expenses ORDER BY amount DESC;
SELECT SUM(amount) FROM expenses;
SELECT category, SUM(amount) FROM expenses GROUP BY category;

That last one is worth sitting with. GROUP BY collapses rows into groups and calculates across each — it's how every "spending by category" report ever built works.

A transaction is a unit of work that either fully succeeds or fully rolls back. Every SQL change — INSERT, UPDATE, DELETE — is part of a transaction. COMMIT finalises it; without it, the change isn't written. ROLLBACK undoes everything since the last commit. SQLite auto-commits many things, but knowing this matters when you write code that makes multiple changes that must all succeed or all fail together.

An index makes queries faster on the columns you search most. Without an index, a query scans every row. With one, it jumps straight to matching rows. The cost is extra space and slightly slower writes. Add an index on any column you frequently put in a WHERE clause:

CREATE INDEX idx_expenses_category ON expenses(category);
Build this

Create the table by hand, insert at least 10 rows across at least 3 categories, and write queries answering: total spend, biggest single expense, total per category, all expenses above average amount. That last one uses a subquery: WHERE amount > (SELECT AVG(amount) FROM expenses). Write it, understand it, and be ready to explain it.

You should now be able to

You can write SELECT, INSERT, WHERE, ORDER BY, GROUP BY and a subquery from memory. You can explain what a transaction is and when to use an index.

Session 2

SQL from Python — and injection

import sqlite3

conn = sqlite3.connect("expenses.db")
conn.row_factory = sqlite3.Row     # get dict-like rows
cursor = conn.cursor()

cursor.execute("SELECT * FROM expenses")
rows = cursor.fetchall()

conn.commit()   # needed after INSERT/UPDATE/DELETE
conn.close()

Now the most important thing in this entire fortnight. Never build a query by joining strings.

# NEVER do this
cursor.execute(f"SELECT * FROM expenses WHERE category = '{category}'")

# do this
cursor.execute("SELECT * FROM expenses WHERE category = ?", (category,))
Why this matters

Imagine a user types ' OR '1'='1 as their category. With the first version your query becomes WHERE category = '' OR '1'='1' — which matches every row. Now imagine they type '; DROP TABLE expenses; --. This is SQL injection, it's been in the OWASP top ten vulnerabilities for over twenty years, and banks have been compromised by it. The fix is always using ? placeholders — the database driver escapes the values safely. Look up "Little Bobby Tables" for the famous version. This applies in every language, every database, forever.

Parameterised queries (using ?) aren't just about security — they're also more reliable with edge cases like apostrophes in names, percent signs, and unicode. Use them for all values, always.

The comma in (category,) isn't a typo — it makes it a tuple of one item.

Build this

database.py with functions for: add, list all, delete by ID, total, filter by category, get by ID, update, and init_db() that creates the table if it doesn't exist. Every single query uses ? placeholders. Zero f-strings in SQL. If you want to verify: grep -n "f\"SELECT\|f\"INSERT\|f\"UPDATE\|f\"DELETE" database.py should return nothing.

You should now be able to

You can explain SQL injection with a concrete example, and you've written no query using string formatting.

Session 3

Swapping the storage out

Replace JSON with SQL inside your storage layer. If project 4 went well, nothing else has to change — the rest of the app doesn't know or care where data comes from.

That's the payoff for separating concerns, and it's worth noticing when it happens. If you do have to change the routes and the templates too, that tells you the layers were more tangled than you thought. Useful information either way.

Write a small script to create the table if it doesn't exist, so a fresh clone works:

def init_db():
    conn = sqlite3.connect(DB_PATH)
    conn.execute("""CREATE TABLE IF NOT EXISTS expenses (...)""")
    conn.commit()
    conn.close()
Build this

App fully on SQLite. Tests updated and green. JSON code deleted.

You should now be able to

Only your storage layer changed, and you can articulate why that's a good sign.

Challenge

No hints — your first database migration

This one is on you

You know SQL, you know Python, you know what a foreign key is from the schema in session 1. Now use all of it. There is no example code.

Add a second table called categories with an id and a name. Move the category strings out of the expenses table and replace them with a category_id foreign key referencing categories.id.

Write a migration script called migrate.py that:

  1. Creates the categories table
  2. Populates it with the distinct category values from the existing expenses data
  3. Adds a category_id column to expenses
  4. Updates every row to point to the correct category ID
  5. Removes the old category text column

After running the script, your app should still work — it will need updating to JOIN the two tables when it needs the category name. Add that JOIN query and make sure all existing features still pass their tests.

Commit the migration script. In a real codebase this is how schemas evolve — you never edit the original CREATE TABLE, you write a migration that transforms the data.

You're done when

The migration script runs cleanly on a fresh copy of the database, the app works with the new schema, and the tests are green.

Session 4

Getting ready to deploy

Your laptop and a server differ in ways that will bite you. Fix them before deploying, not after.

  • Debug off. debug=True shows your source code to anyone who triggers an error. Read the mode from an environment variable.
  • No hardcoded paths. /Users/you/code/... doesn't exist on a server.
  • Port from the environment. The host decides, not you: port = int(os.environ.get("PORT", 5000))
  • A real web server. Flask's built-in server is for development only. It handles one request at a time and isn't built for production traffic. gunicorn is a WSGI server — a proper production server that handles multiple concurrent requests and is designed to be run in front of actual users. pip install gunicorn.
  • Requirements current. pip freeze > requirements.txt

A WSGI server is a standard interface between a Python web app and a web server. Flask implements WSGI. Gunicorn knows how to call it. The deployment platform knows how to call Gunicorn. That's the full stack.

The SECRET_KEY Flask uses to sign session cookies must be a long random string stored as an environment variable — never in your code. If it's in your code, anyone who reads your repo can forge session cookies and impersonate any user. Generate one:

python3 -c "import secrets; print(secrets.token_hex(32))"

Set that as an environment variable, never commit it.

SQLite in production

Most hosts wipe the filesystem on restart, which takes your database with it. Fine for a demo; use the host's managed Postgres if you want the data to survive. Either is a legitimate choice — just make it knowingly.

Build this

Everything configurable via environment variables. Nothing hardcoded. SECRET_KEY generated and stored in .env. Runs locally under gunicorn (gunicorn app:app). A Procfile containing web: gunicorn app:app so the deployment platform knows how to start it.

You should now be able to

Nothing in your code assumes it's on your laptop. You can explain what WSGI is and why gunicorn is needed.

Session 5

Deploying

Pick a host with a free tier — Render, Railway and Fly.io all work. Connect your GitHub repo, set the environment variables in their dashboard, and let it build.

It will probably fail. That's normal and the logs will tell you why. Common causes:

  • A package missing from requirements.txt because you installed it and forgot to freeze
  • Wrong start command — usually gunicorn app:app
  • Ignoring the platform's PORT variable
  • An environment variable set locally but never added to the host
How to debug a failed deploy

Read the build log from the top, not the bottom. The first error is the real one; everything after is fallout. This is true of almost every log you'll ever read.

Build this

A live URL. Send it to three people and watch someone use it on a phone.

You should now be able to

Someone who isn't you has opened your app on a device that isn't yours.

Session 6

After it's live

Watch someone use it without helping. You'll learn more in five minutes than in a week of guessing.

Then tidy: fix whatever they got confused by, check it works on a phone screen, add a custom 404 page and a custom 500 error page so users never see a stack trace, and put the live link at the very top of your README.

Write a short note in your README on what would break if two people used it at the same time. This is about SQLite's limitation: it allows one writer at a time. Two concurrent POST requests — two people adding expenses simultaneously — can cause a locking error. You don't need to fix it, but you need to know about it and say so explicitly.

Take a moment on this one. Twelve weeks ago you couldn't open a terminal.

Build this

Live URL in the README, a screenshot, a simple hand-drawn data model diagram (photograph it), a custom 404 page, a custom 500 error page, a note on the SQLite concurrency limitation, and a paragraph on what you'd do differently.

You should now be able to

It works on a phone, doesn't leak stack traces, and the README is honest about the app's limitations.

Traps to avoid

f-strings in SQL

Always ? placeholders. No exceptions, ever.

Debug mode in production

Shows your source code to the world. Off.

Committing the database file

Add *.db to .gitignore.

Assuming deploy will be quick

Set aside a whole session and expect to spend it reading logs.

If you finish early

  • Add a monthly summary page using GROUP BY on the date.
  • Set up automatic deploys on every push to main.
  • Switch to Postgres on the host's managed database so data survives restarts.
